# 方法報告與技術附錄

## 內容模型

先讀當前實作與文件，確認使用者要說明的是「已部署行為」、「實驗結果」還是「未來設計」。三者可同冊，但不要混成已完成能力。

每個重要處理階段可用以下欄位建立共用資料，再生成表格或段落：

```text
stage_id, purpose, input, transformation, active_settings,
prompt_ref, output_contract, outcomes, limitations,
human_review, source_ref, inspected_at
```

文字順序通常是問題／用途 → 輸入 → 處理 → 輸出 → 如何使用 → 限制。提示詞、長設定及訓練格式放技術附錄；主文解釋其作用，避免反覆貼完整內容。

## 閱讀層次

- **易讀版**：先說能做甚麼、如何解讀結果；用少量對照表和具體例子。
- **詳細版**：保留門檻、提示詞、輸出 schema、例外、覆核與開發歷程。增加分組、書籤及交叉連結，無需為縮頁刪除關鍵細節。
- **技術附錄**：精確設定、完整提示、資料格式、重現步驟及來源索引。可獨立成冊，或保留於完整長報告；按讀者需求決定。

章節 ID 保持穩定，顯示順序與證據 ID 分開。重整後更新 TOC、內鏈、PDF 書籤、簡報與附件索引。目錄不要同時使用 HTML 自動編號和已帶數字的標題而造成重複。

## 工程說明的例子

「固定替換＋LLM 修訂」應說明兩層的任務差異、先後、可接受輸出與保留原文的方式，而非只列兩個模型名稱。若展示轉換前後，標明它是實際執行記錄還是構造例子；沒有執行記錄時不要宣稱該例子已被系統處理。

開發觀察與小樣本結果可並列。例如處理改善了多段錄音、同時部分樣本退步；若機制未被實驗證明，使用「可能損失語音線索」，不要把推測的因果寫成定論。

## 封面與規劃

封面從專案 metadata 讀取 title、author、document_date、edition。資料截止日期另列。沒有使用者提供的作者，不沿用海事範例作者。

工期表要分清 person-days 與 elapsed weeks；標明人力、硬件及外部接入假設。並行工作仍須列相依及里程碑，累計列不能再與分項相加。目標部署硬件沒有實測紀錄時，不列為該硬件測得秒數。

如需教授／研究讀者版本，可採問題、方法、實驗設計、結果、限制及未來工作架構；保留工程證據，不因採論文形式而暗示經同儕審查或已達統計顯著。
